# ADR 0015 gate measurements — 2026-10-12 (#161)

- Commit: `830ddcf` (`main`) for the measured `usage` and `ledger` code.
- Script: `scripts/spikes/adr0015_measure.py`. It is spike code, outside `src/`, because the ADR is
  Proposed. The JSONL side always calls the real `interview_coach.usage` and `interview_coach.ledger`
  functions with an explicit `path=`. The SQLite side prototypes the ADR's schema: WAL,
  `synchronous=NORMAL`, an index on `(day, kind, provider)` and an index on `(session)`.
- Machine: i7-12700H. The `bench` numbers come from btrfs; tmpfs gave the same read numbers to two
  significant figures.

## 1. The gate as written could not be met

The ADR asked for `tests/test_usage.py` to pass **unmodified** on a SQLite backend. That is not
achievable. **34 of its 82 tests exercise the JSONL format itself**: torn lines, unparseable rows,
the `.unreconciled` sidecar (truncation, invalid UTF-8, an unreadable file), file mode bits, and the
order of appended lines. Under SQLite those failure modes do not exist, and different ones take their
place: a locked or busy database, a corrupt database file, a full disk mid-transaction. The gate is
amended accordingly (ADR 0015 §Gate). The 48 behaviour tests must pass unmodified. Each of the 34
format tests is replaced by a test for its SQLite counterpart, or retired with a reason, through a
1:1 mapping recorded in the implementing PR.

## 2. Rail cost: JSONL versus SQLite

One graph-node boundary of `budget_stop_reason` runs three rails: `quota_exhausted_today`,
`session_run_spend` (lifetime spend minus baseline) and `usage_for_day`. #125 counts about two
boundaries per question. The ledgers are synthetic, shaped like the real one (~97% token rows in
Session runs, 30 days, 90% `openai`). Each figure is the median of 15–40 runs.

| rows | JSONL ms / boundary | SQLite ms / boundary | JSONL ms / write | SQLite ms / write |
|---:|---:|---:|---:|---:|
| 1,500 (today's real size) | 7.8 | 0.02 | 0.011 | 0.017 |
| 10,000 | 54.4 | 0.15 | 0.011 | 0.017 |
| 50,000 | 275.8 | 0.73 | 0.011 | 0.016 |

- **Reads scale with the whole ledger under JSONL and with the index under SQLite.** At 50k rows a
  question pays ~550 ms of rail overhead with JSONL and ~1.5 ms with SQLite. That confirms #125's
  extrapolation of 65–72 ms per scan, about 4 scans per boundary.
- **At today's size the read cost is not user-visible:** ~16 ms per question against several seconds
  of LLM time. Speed alone is no reason to switch now. It becomes one as the ledger grows, because
  nothing rotates it (#126).
- **Writes are a wash.** Both are far below 0.1 ms per row against an LLM call that takes seconds.
  Neither fsyncs each row: the JSONL append relies on the OS, and WAL with `synchronous=NORMAL`
  syncs at checkpoints. So the power-loss exposure is the same class, except that SQLite stays
  consistent where a torn JSONL line is skipped.

## 3. Migration dry-run

`migrate` imports a copy, then compares every aggregate the rails and `coach usage` read, Python
against SQL, on every day, provider, Session and identity present. It checks that the stored
original rows round-trip in write order. It backs the database up through SQLite's online backup
API, restores it, and repeats every comparison on the restored copy. It hashes the inputs before
and after.

| Input | Rows | Comparisons | Mismatches | Restored copy | Inputs unchanged |
|---|---:|---:|---:|---|---|
| local dev usage ledger (`logs/usage-ledger.jsonl`) | 1,512 | 21 | **0** | 0 mismatches | yes |
| container state volume: usage ledger | 17 | 7 | **0** | 0 mismatches | yes |
| container state volume: Skill ledger, 3 Candidates | 3 records | `load_priors` per Candidate | **0** (identical) | — | yes |
| synthetic edge ledger (see below) | 5,956 (+44 torn) | 164 | **0** | 0 mismatches | yes |

The real ledgers contain only 4 row kinds over 4 days, so the edge ledger exists to exercise what
they do not:
- `quota_exhausted` and `quota_retry`, both granted and session-scoped (the latch is order-sensitive);
- releases that exceed reservations (the never-negative clamp);
- token rows with non-integer values;
- `session_run` rows with a bad baseline;
- torn lines.

**The harness can fail.** With the clamp removed from the SQL twin of `questions_today`, the same run
reports `MISMATCH questions_today(2026-10-01): python=0 sql=-8`, and more like it.

## 4. What this does and does not settle

- **Settled:** the import is lossless on every real ledger this project has, and on the edge cases
  it lacks. An indexed read makes the rails' cost independent of ledger size. Writes cost the same.
  A backup/restore through the SQLite API reproduces every number.
- **Not settled:**
  - The concurrency semantics under load: `BEGIN IMMEDIATE` replacing `_FAULT_LOCK`,
    `_LEDGER_WRITE_LOCK` and `flock`. That needs the implementation and the #122/#123 race tests
    ported to it.
  - The cost of the 34 test replacements.
  - Behaviour on a network filesystem: SQLite WAL needs a local disk. The deployment's named volume
    is local, so this does not block the pilot.

**Recommendation: Accept.** The case is not speed at today's size. It is that one transactional
store retires a whole class of defects (#123, M0-12 and #122 were all lock choreography), gives #127
its history for free, which unblocks #83, and makes #126's retention a `DELETE`. The measurements
remove the two risks a migration carries: losing data, and making the hot path slower.
